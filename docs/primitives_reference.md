# Primitive Reference

This document describes the primitive skills referenced by HumanoidSim task steps. A primitive is the smallest executable skill in the task hierarchy, and task leaf steps reference primitives with `expected_level=PRIMITIVE_SKILL`.

## Summary

- Registry primitives: 59
- Active primitives: 59
- Source primitive definitions: `data/primitives/*.json`
- Source state relation data: `metadata.state` in each primitive JSON and `primitive_state_profiles` in `data/state_schema_core.json`
- Every primitive that is running normally is represented as `availability=EXECUTING`.

## Active Primitive vs Registry Primitive

| Term | Meaning | Source | Purpose |
| --- | --- | --- | --- |
| Active primitive | A primitive directly referenced by the current task catalog with `expected_level=PRIMITIVE_SKILL`. It appears as an executable leaf step when a task is expanded. | `data/tasks/*.json` -> `steps[].call_code` | Task reference, execution coverage, ManSim support checks |
| Registry primitive | Any primitive registered in HumanoidSim. It may exist for future custom tasks even if no current task references it. | `data/primitives/*.json`, primitive entries in `data/task_catalog_core.json` | Schema validation, hierarchy validation, custom task extension |

In v0.1, active primitives and registry primitives are both 59. Conceptually, active primitives are a subset of registry primitives.

## Primitive and State Relation

Primitive tells what execution step the humanoid is performing. State tells what operational condition the humanoid is in while performing that step. Therefore a primitive is not itself a state, but primitive start/end events drive state transitions through HumanoidSim.

| Field | Meaning |
| --- | --- |
| `metadata.state.availability.running` | Availability State while the primitive is running. Every primitive uses `EXECUTING`. |
| `metadata.state.allowed.mobility` | Mobility states allowed while the primitive is active or ending. |
| `metadata.state.allowed.manipulation` | Manipulation states allowed while the primitive is active or ending. |
| `metadata.state.allowed.power` | Power states allowed while the primitive is active or ending. |
| `metadata.state.effects.on_start` | State effects applied when the primitive starts. |
| `metadata.state.effects.on_end` | State effects applied when the primitive ends. |

Examples: `NAVIGATE_TO` starts with `mobility=NAVIGATING` and ends with `mobility=STATIONARY`. `GRASP` and `LIFT` use `manipulation=HOLDING`. `PLACE` and `RELEASE` use `PLACING` while placing and return to `FREE` at the end. Record/check primitives are usually `STATIONARY` and preserve cargo-related manipulation unless a caller cargo event changes it.

## Adding a New Primitive

1. Add `data/primitives/<CODE>.json`.
2. Define `metadata.state.availability.running`, `allowed`, `effects.on_start`, and `effects.on_end`.
3. Add the same profile to `primitive_state_profiles` in `data/state_schema_core.json`.
4. Reference it from task steps with `call_code=<CODE>` and `expected_level=PRIMITIVE_SKILL`.
5. Run `python -m unittest discover -s tests` to validate primitive profiles and task hierarchy.
